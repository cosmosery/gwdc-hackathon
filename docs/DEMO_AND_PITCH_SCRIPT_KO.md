# Settle — 3분 데모 촬영안과 5분 발표 초안

작성 기준: 2026-09-30. 현재 코드와 실제 Nile 검증 결과 기준이다. 이 문서는 촬영 계획이며 영상·공개 링크·PDF/PPT가 제작됐다는 뜻은 아니다.

## 1. 제출 요구사항과 발표 방향

- 제출용 데모: 최대 3분. Notion / Google Drive / YouTube 공개 링크. 로그인하지 않은 창에서 접근 확인.
- 데모는 제품 워크플로와 AI 의사결정 과정을 보여야 한다.
- 피치덱: PDF 또는 PPT. 팀, 프로젝트 개요, 문제·해결책, 제품, 기술, 시장·경쟁, 로드맵, 사업성과 장기 비전 포함.
- 5분 발표와 3분 제출 영상은 별도 편집한다. 5분 발표에서 3분 영상 전체를 틀지 않고 약 90초의 핵심 컷을 쓴다.
- 중심 문장: **“한 번의 GasFree 입금에서 시작해, 지급 목록의 각 행을 검증 가능한 결과로 돌려준다.”**
- 구조 후보는 세 가지, 약 40초만 설명한다. 장애 조사와 개발 시간순 회고는 Q&A 자료로 남긴다.

## 2. 촬영 전에 필요한 마무리

| 항목 | 현재 상태 | 제출 전 필요한 일 |
|---|---|---|
| 실제 AI 판단 | 라이브 UI는 `AI review · not connected`. 규칙 검사는 작동한다 | 실제 모델에 업무 메모·금액 차이·규칙 결과를 입력하고 추천·근거·모델·시간·사람의 최종 결정을 기록. 고정 문구나 규칙 검사를 LLM 판단으로 소개하지 않음 |
| CSV 원본과 결과 연결 | API는 index/주소/금액/tx를 제공하지만 현재 결과 화면에서 이름·업무 메모 원본이 복원되지 않음 | 원본 행 ID/이름/메모와 payment index를 보존·연결해 결과 CSV까지 검증. 같은 주소 여러 행도 구분 |

AI와 원본 행 연결은 Challenge C 요구에 직접 연결된 미완료 항목이다. 설명 영상만으로 완료를 대신하지 않는다.

## 3. 시나리오를 가장 짧게 보여주는 구성

모든 장애를 3분 안에 실제로 발생시키지 않는다. 주 영상은 하나의 지급 업무를 끝까지 따라가고, 복구는 짧은 별도 검증 컷으로 보여준다. 추가 상세 영상은 선택 자료로 두되 필수 영상은 자체적으로 완결되게 만든다.

| 시나리오 | 촬영 화면·행동 | 전달할 메시지 | 증거/준비 |
|---|---|---|---|
| 정상 지급 | 소액 CSV → 견적 → TronLink 송금 → 입금 확인 → 지급 → tx 링크 | 실제 지급과 결과 추적 | 새 1행 배치로 녹화 권장. 기존 3행 배치는 보조 증거 |
| 주소 오류 | 한 행의 주소 체크섬 오류 → 해당 행 제외/수정 | 지급 전에 오류 차단 | 실제 파서·검증기 |
| 업무상 금액 차이 | expected_amount와 amount 차이, 관련 메모 → AI의 보류 근거 → 사람이 결정 | AI는 맥락을 설명하고 사람은 승인 | 실제 AI 연결 후 촬영. 현 상태는 규칙 기반 경고만 시연 가능 |
| 부족한 입금 | 미입금/부분입금 배치의 대기 화면 | 입금 확인과 지급 성공은 다른 상태 | 격리 테스트 결과를 사용하면 반드시 환경 자막 |
| 타임아웃·중복 방지 | 테스트 실행과 기존 지급 기록 유지 | 응답 없음 ≠ 실패. 기존 거래부터 확인 | 장애 주입 검증 컷. 실제 테스트넷 장애라고 표현하지 않음 |
| 부분 실패·복구 | 성공 행 보존, 미확정 행 조사/복구 | 이미 지급한 행을 다시 지급하지 않음 | 현재 라이브 UI에 해당 장애 배치가 없으면 테스트 결과 화면으로만 제시 |
| 만료 환불 | 기존 환불 tx와 고정 수령 주소 | 미지급 원금은 만료 등 계약 조건에 따라 회수 | artifacts/nile-expired-refund.json. 만료 fixture를 사용한 실제 Nile 환불임을 명시 |

권장 주 영상은 정상 지급 + 입력 오류 + AI 판단 + 복구 원칙이다. 부분입금·환불 전체 시연은 3분 영상에 억지로 넣지 않는다.

목표 파일 길이는 2:55로 두고 인트로·아웃트로 포함 3:00을 넘기지 않는다. 블록 확정 시간은 통제할 수 없으므로 라이브 무편집 완료를 전제로 구성하지 않는다.

### 촬영 파일 구성

1. `01-review`: 오류·금액 차이가 있는 목록. 검토 장면에서 실제 제외/수정 과정까지 녹화.
2. `02-payment`: 검토를 마친 같은 목록에서 소액 한 행만 실제 지급. 목록을 바꾸면 화면에 변경 사실을 밝힌다.
3. `03-confirmation`: 그 배치의 완료·tx·보고서. 대기 구간만 편집하고 batchId를 유지.
4. `04-recovery`: 격리 테스트 화면. 제품 실거래 컷과 자막으로 구분.

기존 성공 배치로 컷을 전환해야 하면 “이전 Nile 검증 배치”라고 명시한다. 같은 주소에 지급한 세 행을 서로 다른 세 사람이라고 소개하지 않는다. 지갑 승인이나 진행률을 사후 합성하지 않는다.

## 5. 구조 후보 설명용 한 장

| 후보 | 간단한 흐름 | 장점 | 이번 선택에서 제외/유보한 이유 |
|---|---|---|---|
| 행별 GasFree 직접 지급 | CSV N행 → 필요한 N개의 지급 승인 → N개의 GasFree 지급 | 과제의 행별 GasFree 추적과 가장 직접적으로 대응. 별도 지급 계약 부담이 적음 | 승인 조율과 건별 Provider 수수료 부담. 여전히 유효한 비교 기준이며 기술적으로 불가능해서 버린 것은 아님 |
| 플랫폼 입금·자동 서명 | 사용자 → 플랫폼 지갑 → 플랫폼이 수취인 송금 | 운영 구현과 사용자 동선이 단순 | 플랫폼 키의 지급 권한·자금 보관·잔액 관리 부담. 키 유출이나 운영 실수가 자금에 영향을 줄 수 있음 |
| 배치별 BatchExecutor | 사용자 GasFree → 전용 Executor → 행별 지급 | 한 번의 입금으로 여러 행을 처리. 계약에 고정된 목록과 중복 방지 조건을 사용 | 채택. 추가 계약 검증·배포·릴레이어 자원 비용을 감수해야 함 |

MPC/Vault는 플랫폼 키 보관 위험을 줄이는 추가 수단이지, 그 자체로 지급 목적지 제한이나 수탁 모델을 제거하지 않는다. 본 발표에서는 별도 후보로 길게 설명하지 않고 Q&A에서 다룬다.

현재 구현은 수취인마다 별도 `execute` 트랜잭션을 보내는 방식이다. N명을 한 온체인 트랜잭션으로 보내는 `executeBatch` 구현이라고 말하지 않는다. 행별 확정·복구가 쉽지만 순차 확정으로 시간이 늘어난다.

GasFree Provider 비용을 한 번의 입금에 모으더라도 전체 비용에는 배포와 N건 지급의 TRON 자원이 추가된다. “항상 더 싸다”, “수수료가 전체 한 번뿐이다”, “100명 비용 검증 완료”는 현재 증거로 주장하지 않는다.

현재 지갑 동선: CSV → 검토 → 견적 → 배치 주소 생성 → TronLink 내부 GasFree 송금 → 체인 잔액 확인 → 지급 시작 → 행별 확정·보고.

## 6. 5분 발표 대본 초안 — 현재 구현에 맞춘 버전

괄호 안은 무대 큐이며 읽지 않는다. 시연 조작·전환 시간을 포함한 배분이다. 실제 말속도에 맞춰 리허설에서 조정한다. 팀 이름과 구성원 정보는 제공되지 않아 만들지 않았다.

### 0:00–0:30 | 문제·팀 소개

안녕하세요. 저희는 스테이블코인 팀 지급을 위한 Settle을 만들었습니다.

회사가 외부 작업자들에게 지급한다고 생각해 보겠습니다. 담당자가 가진 것은 이름, 지갑 주소, 금액, 업무 메모가 담긴 CSV입니다. 하지만 실제 업무는 송금에서 끝나지 않습니다. 잘못된 주소를 발견하고, 금액이 맞는지 확인하고, 누가 받았는지 다시 기록해야 합니다. 저희는 이 전체 과정을 하나로 연결하고자 했습니다.

### 0:30–1:00 | GasFree의 특징과 우리가 더하는 가치

GasFree는 사용자가 TRX를 따로 준비하지 않고, 스테이블코인으로 수수료를 내며 송금할 수 있게 합니다. 수수료가 없어지는 것은 아닙니다. 사용자 승인에 따라 Provider가 전송을 처리하고 비용을 받는 구조입니다.

저희는 그 위에 기업 지급 업무를 얹었습니다. 지급 전 목록 검토부터, 승인한 지급의 실행, 건별 상태 추적과 결과 정리까지 담당하는 것입니다.

### 1:00–1:45 | 검토한 세 가지 구조와 선택

세 가지 방법을 비교했습니다.

첫째는 각 행을 GasFree로 직접 보내는 방식입니다. 가장 직접적이지만, 행마다 필요한 승인과 수수료를 조율해야 합니다.

둘째는 플랫폼 지갑으로 돈을 받은 뒤 자동 송금하는 방식입니다. 편리하지만 플랫폼이 자금을 보관하고 지급 권한을 관리해야 합니다.

그래서 배치별 전용 계약인 BatchExecutor를 선택했습니다. GasFree로 총 지급액을 한 번 입금하고, 엔진이 계약에 고정된 목록을 따라 각 행을 지급합니다. 계약은 수취인과 금액의 증명, 이미 지급한 행인지 여부를 검사합니다. 다만 이후 지급의 네트워크 비용은 따로 발생하며, 현재는 운영자가 부담합니다.

### 1:45–2:10 | 현재 지갑 연동과 수수료 경계

현재 테스트한 TronLink는 웹사이트의 PermitTransfer 요청을 제한했습니다. 그래서 배치 주소를 먼저 만들고, 사용자가 TronLink 내부 GasFree 화면에서 송금을 승인하도록 연결했습니다. 사용자 개인키는 지갑에 남습니다.

앱에는 예상 수수료를 보여주되, 실제 승인 금액은 지갑에서 확인합니다. 수동 경로의 예산 여유 값이 지갑 수수료를 강제로 제한하는 것은 아닙니다.

### 2:10–3:40 | 제품 데모 — 약 90초 핵심 컷

(CSV 업로드)

파일을 넣어도 돈이 움직이지 않습니다. 먼저 지급 목록을 검토합니다. 잘못된 주소는 차단하고, 예상 금액과 다른 행은 담당자가 확인하도록 표시합니다.

(현재 구현에 맞춘 AI 설명)

여기까지는 규칙 검사입니다. AI는 업무 메모와 금액 차이를 함께 보고 보류 여부와 근거를 제안하는 역할로 설계했습니다. 현재 라이브 모델 연결은 남아 있어, 지금 보이는 경고를 AI의 판단이라고 소개하지는 않겠습니다. 최종 지급 결정과 지갑 승인은 사용자에게 있습니다.

(견적 → 배치 주소 → TronLink 승인)

검토한 원금과 예상 비용을 확인하고 배치 주소를 만듭니다. 이제 지갑에서 송금을 승인합니다.

(입금 확인 → 지급 진행. 대기 생략 자막)

엔진은 실제 입금을 확인한 다음 지급을 시작합니다. 진행률은 시간이 흘렀다는 이유로 올라가지 않습니다. 각 지급의 결과가 확인돼야 반영됩니다.

(실제 결과 화면·트랜잭션 링크)

이것은 Nile에서 실제 완료된 테스트입니다. 동일한 테스트 수취 주소에 0.01, 0.02, 0.03 USDT를 세 행으로 지급했고, 각 행의 거래 해시를 확인할 수 있습니다. 이 화면은 기존 검증 배치입니다.

### 3:40–4:10 | 실패·복구·검증의 의미

기업 지급에서는 성공만큼 결과를 모를 때의 행동도 중요합니다.

저희는 응답이 끊겼다고 바로 새 송금을 만들지 않고 기존 거래부터 확인합니다. 이미 지급된 행은 중복 지급 검사로 보호합니다. 이러한 상황은 장애 주입 테스트로 검증했고, 실제 Nile에서는 지급과 만료 후 미지급 원금 회수도 확인했습니다.

지급 성공과 정산 증거의 완성도 구분합니다. 확인되지 않은 비용을 실제 비용이라고 채워 넣지 않습니다.

### 4:10–4:40 | 초기 고객·사업성

초기 고객은 USDT로 프리랜서나 외부 파트너에게 반복 지급하는 팀입니다. 이들이 줄이려는 비용에는 송금 비용뿐 아니라, 검토와 대사에 드는 시간도 있습니다.

일반 지갑과 비교한 Settle의 가치는 지급 목록과 업무 맥락, 실행 결과를 한 과정에 담는 데 있습니다. 수익 모델은 팀 구독과 사용량 기반 과금을 검증할 계획입니다. 아직 고객 매출이나 비용 절감률을 확인한 단계는 아닙니다.

### 4:40–5:00 | 로드맵·마무리

다음 단계는 실제 AI 검토와 원본 행의 정산 연결을 완성하고, 지갑 연동과 계약 보안을 강화하는 것입니다. 이후 팀 승인 절차와 회계 도구 연동으로 확장하겠습니다.

Settle은 GasFree의 한 번의 송금을, 팀이 끝까지 확인할 수 있는 지급 업무로 연결합니다. 감사합니다.

### 실제 AI 연결 후 교체할 20초 대사

“주소 오류는 규칙으로 검사합니다. 이 행은 주소가 맞지만, 예상 금액과 지급액이 다릅니다. AI는 업무 메모까지 읽고 증액 근거가 충분하지 않다며 보류를 권고합니다. 여기서 입력, 근거와 추천을 확인할 수 있습니다. AI가 금액을 고치거나 송금하지는 않습니다. 담당자가 수정·제외·포함을 결정합니다.”

실제 모델이 그 추천을 반환하고 기록한 경우에만 사용한다. 반대 추천을 반환하면 결과를 숨기지 말고 해당 설명을 맞춘다. 특정 문구를 얻기 위한 재시도를 정상 1회 응답처럼 편집하지 않는다.

## 7. 피치덱 권장 7장

1. **Settle / 팀**: 한 문장 가치와 실제 구성원·역할.
2. **문제**: CSV → 지갑 → 거래내역 → 수작업 대사의 단절. 고객 인터뷰나 숫자는 확보한 것만.
3. **GasFree + 구조 선택**: 직접 지급 / 플랫폼 지갑 / BatchExecutor 비교. 채택 구조에 설명 집중.
4. **제품 데모**: 90초 핵심 컷. 실제 테스트넷·대기 생략·장애 주입 표기.
5. **검증·복구**: 실제 지급 tx, 중복 방지/타임아웃 테스트, 알려진 구현 범위.
6. **고객·경쟁·수익 모델**: 초기 고객, 일반 지갑·수작업·기업 지급 도구와의 기능 비교. 가격·시장 규모는 추가 조사 후 출처와 함께.
7. **로드맵·비전**: AI·원본 행 연결 → 지갑/보안/자원 운영 → 팀 승인·회계 연동. 다음 검증 목표를 명시.

## 8. 촬영 전 최종 확인

- 개인정보·키·Secret·Bearer가 녹화에 노출되지 않게 창을 정리한다. 공개 가능한 테스트 주소·tx만 사용.
- 한 행 소액 지급으로 수정 UI 전체 리허설. 이전 `execute-direct` 오류 경로를 사용하지 않는지 확인.
- batchId를 컷 사이에 유지. 기존 배치를 대신 보여주면 명시.
- AI 모델의 실제 응답·근거·시간과 사람의 결정을 보존.
- 수수료 견적과 실제 청구를 구분. 미사용 maxFee는 미청구 한도이며 원금 환불과 다름.
- 실패 시나리오에 격리 테스트 자막. 모든 테스트가 실제 Nile 실거래였다고 표현하지 않음.
- 성공 3행이 동일 주소 지급임을 정확히 설명.
- 제출 영상 전체 3분 이내, 공개 접근 확인. 피치덱 PDF/PPT는 별도 제작·검수.
